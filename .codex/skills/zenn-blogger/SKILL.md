## 成果

読者が題材の価値と適用条件を短時間で判断でき、根拠をたどれる日本語の技術記事にする。記事の魅力は誇張ではなく、具体性と検証可能性でつくる。

## 執筆の進め方

1. 新規記事または全面改稿は、必ず `articles/_template.md` を複製して始める。テンプレート自体は変更しない。
2. 読者、解決する課題、記事で扱わない範囲を定める。
3. 実際のコードを題材にする場合は、先にリポジトリを調べる。本文は一般的な課題として説明し、実装例だけを実コードに基づける。固有のデータ名や研究分野は、理解に必要な場合だけ残す。
4. 仕様・API・数値・製品の現行動作などの事実は、一次情報（公式ドキュメント、仕様、一次発表）で確認する。時間に依存する内容は確認日を意識し、本文では必要な箇所に直接リンクを付ける。
5. 主張を「事実」「実践上の解釈」「筆者の判断」に分ける。根拠のない一般化や、出典のない比較はしない。
6. 複数のアプローチが成り立つ場合は、各案の向く条件・利点・制約を説明する。一つを正解として他を退けるのではなく、読者が選べる材料を示す。
7. テンプレートのプレースホルダーと HTML コメントをすべて置き換えまたは削除し、Zenn の Front Matter を内容に合わせる。`npm run lint` で確認する。

## テンプレートの使い方

`articles/_template.md` 内のコメントは必須の執筆指示として扱う。

- 見出しは、その節の本文を簡潔に表す自然な日本語にする。本文の結論を見出しにせず、直前の節を読んだ読者が次に知りたいことを表す。
- 最初の節では、読者が困っていることを箇条書きで簡潔に示す。
- 「何をするか」では、具体的な実装手段に入らず、解決の考え方を説明する。
- 「どうするか」では、読者が知りたい順に技術詳細を書く。コードは必要な箇所だけを短く掲載する。
- まとめでは、導入によって何が変わるかを簡潔に示す。

狭い修正では既存記事の構成を不必要に変えない。ただし、新規記事と全面改稿ではこの構成を守る。

## 課題をつなぐ構成

- 冒頭に `:::details この記事で分かること` を置き、2〜4項目で要約する。各項目には、採用する技術と解決する課題を具体的に書く。「〜する方法」のような抽象的な表現だけで終えない。
- 導入は、筆者の経験、繰り返し発生した処理、困ったこと、採用した考え方の順につなぐ。一文ごとの因果関係を確認する。
- 機能を順に紹介するのではなく、一つの課題を解決すると次の制約が現れる流れにする。各節の末尾で残る課題を示し、次の節の冒頭で受ける。
- 各節は、問題のある実装、問題が起きる理由、修正後のコード、適用条件や残る制約の順を基本とする。
- 用語は初出より前か直後に短く定義する。製品やライブラリの説明は、記事内で使う特徴に絞る。
- まとめは、タイトルと冒頭の要約に対応させる。本文で扱っていない主張を追加しない。

## コードの扱い

- 一般的なデータ名と小さな例を使い、読者が自分の処理へ置き換えられる形にする。
- アンチパターンは問題が分かる最小限のコードにする。改善後のコードでは、どのデータがメモリ、ディスク、外部ライブラリに保持されるかを説明する。
- 同じ概念には同じ変数名、列名、ファイル名を使う。節をまたいで入力と出力がつながるか確認する。
- 全件処理、遅延実行、ストリーミング、バッチ処理を混同しない。メモリを抑える範囲と、最終的に具体化される範囲を分けて書く。
- コードで使う依存関係と対象バージョンを明記する。不安定な API は、その制約と採用範囲を説明する。
- 実行できるコードは対象バージョンで試す。省略した関数やスキーマがある場合は、その役割をコードの直後に示す。
- 条件を揃えた計測がない場合は、速度やメモリ使用量を数値で比較しない。代わりに、不要になる読込や全件保持をコードから確認できるようにする。

## 文体

- `です・ます`調で、短く具体的に書く。大学院生が技術を説明するような、自然で落ち着いた語調にする。
- 「この記事の主題は」のような硬い言い回しより、「この記事では」のような簡単な表現を使う。
- 「〜については説明しません」のように、記載しない内容を列挙しない。「〜を例とします」より、必要なら「〜を例とすると」と本文へつなぐ。
- 「〜する方法」が冗長なら、「〜を採用」「〜で回避」「〜を確認」のように、技術と結果を直接書く。
- 略語は慣例的で、読者層に通じるものだけを使う。必要なら初出で正式名称を示し、そうでなければ「自前実装の関数」のような具体的な日本語へ置き換える。
- 煽り、過剰な導入、冗長な比喩、根拠のない「必須」「最適」は使わない。
- 導入で課題と結論を示し、本文ではコード、設定例、判断基準、失敗しやすい点を必要な分だけ扱う。
- 読者を引きつける目的だけの問いかけや Before/After 演出は避ける。
- 公式情報は「公式ガイドでも説明されています」と紹介せず、関連する主張の直後に `参照: [資料名](URL)` と置く。
- 既存の公開記事を改稿するときは、公開済みの事実関係を変える根拠と影響を確認する。

## 完了条件

- 主要な事実に出典があり、リンク先が主張を直接支えている。
- 異なる実践がある論点では、選択条件を説明している。
- 冒頭から通読し、段落間と節間で「前の文を受けて次の文が続くか」を確認している。
- タイトル、冒頭の要約、導入、本文、まとめの対象範囲が一致している。旧タイトルや削除した前提への言及が残っていない。
- コード内の変数名、列名、ファイル名、型、依存関係が本文と一致している。
- 記事の Front Matter と Markdown lint が通る。
